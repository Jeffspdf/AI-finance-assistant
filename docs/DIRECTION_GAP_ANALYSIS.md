依据：用户提供的《项目方向与改造说明_交给Codex.md》，并逐项核对现有业务代码、桌面入口、测试及工程文档。该外部说明是待核实的产品建议，其中的目标值不作为已实现能力或已取得的评测结果。

本轮交付为差距分析和架构决策草案。当前可运行的软件继续作为兼容性基线。本文保留既有Windows安装/快捷方式/更新渠道、Python、Tkinter、SQLite、中文名称及校园角色。

## 1. 方向判断

建议采用“本地优先的月度账单复盘助手”定位。现有产品已能完成导入、分类、预算、目标和有依据问答；下一步价值应来自账单处理的正确性及闭环，而不只是增加模型或界面入口。

当前已经具备：整数分存储、确定性金额计算、CSV/XLSX通用解析、同源身份去重、异常预览/导出、商户分类记忆、预算/目标进度、会话问答、可选模型、Windows安装更新和DPI适配。

当前最重要的缺口：

1. **跨源对账缺失。** 微信与银行卡描述同一消费的两条记录仍分别计入支出；已有查重只是交易身份查重。
2. **原始导入证据不足。** 仅保存规范化后的交易、文件名和行号，没有文件内容哈希、完整原始行及导入批次记录。被跳过的重复/退款行无法在库中重放。
3. **证据“存在”与证据“完整”不同。** 异常卡历史均值的历史记录没有附到依据中；目标预测还需要目标及实际存入数据，不能仅靠交易ID复算。
4. **退款语义不完整。** 已退款/退款成功状态会被跳过；其他退款状态进入异常，没有原消费、部分退款、退款日期与净支出的统一口径。
5. **新目标缺少评测。** 没有真实分类标注集、跨源重复标注集、5万行可取消基准或5人可用性测试。

## 3. 本轮定向复现

在临时数据库或内存DataFrame中执行四个小样例，数据均为合成，没有读取个人账本或调用模型。

| 样例 | 实际观察 | 意义 |
|---|---|---|
| 同日同商户60元，微信ID和银行卡ID各一条 | 存2条，支出12000分 | 证明没有跨源排重；这两条是否同一笔仍需来源语义和用户确认，不能仅凭相同金额自动修正为60元。 |
| 100元成功消费+100元“退款成功”行 | 规范化1条，skipped=1，issues=0，支出10000分 | 证明该退款路径既没有冲减，也没有进入可见退款复核队列；不能宣称支持退款净支出。 |
| 7/8月餐饮各100元、9月300元 | 异常卡显示历史均值100元、3倍，只附9月ID `sep` | 结论的算式可由全体数据复算，当前卡片证据不足以复算历史均值。 |
| 8月餐饮100元、9月仅交通10元 | 只生成“交通较上月增加” | 餐饮从100元降为无匹配记录的变化没有候选；后续表述必须强调已导入范围，不能推断真实消费归零。 |

v0.7.1最近已验证的基线为94项回归、DPI与打包运行检查。四个定向复现说明现有验收范围的边界；旧测试通过不意味着新方向的验收已通过。

## 4. 关键取舍

详见[ADR草案](adr/0001-monthly-review-incremental-plan.md)。以下是实施前要固定的技术口径：

- **保留Windows桌面交付。** Python/Tkinter/SQLite已有安装与更新资产，无需为此方向切换Web或Java；业务核心继续与UI解耦。
- **先证据补强，再扩大模型能力。** 模型能输出合法JSON不代表查询、基线和解释都完整；所有结果要能用原始输入及确定性代码重放。
- **跨源候选默认不改变金额。** 第一版人工确认后才单次计数，避免错合并；同源已验证ID重复可不再新增规范交易，但每次来源/结果需留痕。
- **原始记录与统计投影分离。** 账本展示原始规范交易/关联状态；分析通过统一投影取确认组代表。概览、预算、规划、洞察、问答和旧Web原型必须使用同一规则。
- **退款关联与重复关联分开。** 完整/部分退款不是第二条相同消费。退款先入复核并保留原状态；净支出/月度归属需要显式口径，不能悄悄改变既有income/expense含义。
- **保留显式分类学习。** 用户错误分类不应被自动记成永久规则；完全匹配merchant+kind继续作为第一版边界。
- **小步提取服务。** 先提Import与Analysis入口，保留旧函数的兼容包装；不先造一整套仓储/依赖注入框架。

## 6. 迁移与恢复风险

1. **迁移前备份。** 使用SQLite backup API生成一致快照，校验可打开和关键表计数；不能把运行中的数据库文件直接复制视为完整备份。确认备份成功后才更新模式。
2. **版本单向检查。** 修复后的新程序只迁移已知旧版本，发现数据库高于自身支持时拒绝写入。无法回溯改变已分发旧程序，旧版仍可能覆盖user_version；因此不支持直接降级，应使用对应版本备份。迁移在事务中完成，故障不留下半套表/索引。
3. **不重建旧来源。** 旧交易保留ID、signature、金额、人工分类、文件名及行号。无法取得旧原始文件时标注legacy，RawRow引用允许缺失；不生成看似真实的raw_json/文件哈希。
4. **审计追加。** 新增、改分类、模型接受、关联、拆分、删除/恢复都追加事件；undo也有事件。事件快照的隐私与用户账本相同，留在本机，不进入公开仓库。
5. **数据回滚与程序回滚区分。** 若新版已写入关联/退款，旧程序即便能打开，也会忽略新统计口径；切回旧版应恢复对应版本备份。恢复应预览/确认并保留恢复前快照。
6. **双空间独立。** demo/personal分库、设置与新批次信息保持隔离；只用临时旧库副本测试，迁移不能借助演示库假装个人库已验证。

## 7. 验收缺口与测量方式

- **格式**：三类指定版本的原始/预期文件，按记录逐字段比较，覆盖编码、前导说明、符号金额、状态、退款、多个工作表、CSV引号换行及行号定义。通用XLSX模板通过不等于某家银行全部格式通过。
- **身份/对账**：区分同源ID、同源无ID、跨源重复、两笔相同消费、信用卡还款与消费、三条候选冲突、用户排除后重导、编辑后关联失效、拆分与统计重算；候选阈值与评估集分离。
- **证据**：不能只检查“返回ID存在”。逐个核对数值、角色、分子/分母、时间范围、退款/关联状态和配置快照；对目标实际存入用Contribution证据，对预算用Budget来源。
- **分类**：覆盖率=无需人工处理的有效规范交易数/有效规范交易总数；准确率按独立人工标签计算。样本来源、版本和抽样方式一并记录。已有100条合成分类回归不是实际用户准确率。
- **性能/取消**：5万行分格式，分别记录读取/解析/规范化/数据库提交时间、峰值内存、UI心跳及取消响应时间；行数上限不是性能保证。取消中止工作和取消后无入库分别验证。
- **安全/离线**：覆盖默认操作无请求、网络故障仍可复盘、密钥不写盘、导出日志不含密钥；分类描述/用户问题含提示注入时仍只产生白名单字段，不执行SQL或写操作。
- **可用性**：从“用户已导出文件并启动应用”到第一条可解释洞察计时；不承诺平台导出本身只需30秒。3分钟、80%、100%/0均为目标，应附实测范围及失败，不写成无条件产品保证。

## 8. 尚缺的信息与默认推进边界

目前已能确定继续桌面端、本地优先、中文界面、保留校园角色与可选模型，不重复询问这些偏好。目标用户暂按课程场景以大学生为优先。

特定银行/导出版本、脱敏真实样本与双人标签、可调用模型、可用性测试人员及时间预算仍待后续补充。这些信息不阻塞P0和迁移/合成夹具工作；但没有它们就不能宣称真实格式兼容率、模型效果、对账准确率或用户完成时间达标。

**建议下一批实施P0：补齐异常洞察历史证据、修正环比候选范围、明确不同洞察的卡位和公式来源。之后进入带备份的M1迁移。**
