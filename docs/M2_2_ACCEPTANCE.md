# M2-2：退款决定与净额投影验收包

日期：2026-11-04。基线：用户已通过的M2-1提交`cd7d7c6`。分支：`m2/refund-net`。本包交付服务层：退款确认/撤销、退款事件去重、全局重验、只读`spending_view`及常规失效钩子。**界面统一接入是M2-4，当前不是可发布的完整客户端。**

## 对评审四点的独立判断与实现

| 项目 | 判断及结果 |
|---|---|
| 退款源状态 | 采用A。源行一直保留`refund_pending`，不写`refund_linked`。`refund_sources()`派生`linked/pending/needs_review`；`pending_refunds()`只汇总没有有效确认的逻辑退款，已去重的微信/银行退款只算一个事件。失效confirmed也回待处理。 |
| 分类域 | 问题成立：M2-1只排除了转账分类。现在`_source`调用`validate_kind_category`，消费组的每个来源也要校验。“支出+工资”“收入+餐饮”拒绝关联，明确提示先去历史分类待修正；不自动改旧分类。 |
| 全局唯一/上限 | M2-1局部校验本来能挡住大多数正常换资金腿的路径，不能说完全无防护；但确实缺少对库内既有异常的整体检查。新增`assess_confirmed_links`重验全部confirmed：同一退款事件只能一次、同一消费事件累计不超额、上下文一致。异常关联及相连决定全部转为读取时待复核，不挑一条保留。 |
| 确认事务 | `BEGIN IMMEDIATE`→全部confirmed重验→重新校验新关联→写关系→写审计→提交。异常时抛带`status=needs_review`和关联ID的明确错误，不写新确认。UI预览不接受为确认凭据。 |

全局异常会阻止新确认，避免在已有不一致的账本上继续增加决定；撤销等纠错动作仍可执行。只读投影仅屏蔽失效的相关组件，保留无关有效退款。普通消费和退款源的金额、日期、类型不因确认而改变。

## 服务与投影契约

| 接口 | 契约 |
|---|---|
| `validate_refund_link` | 只读预览，不预留额度。 |
| `confirm_refund_link` | 全局重验、归一化事件代表、整笔退款关联一个消费；新增/重新确认均保留旧新审计快照。 |
| `revoke_refund_link` | 状态转rejected，撤销抵扣；保留来源、上下文和审计，可明确重新确认。撤销失效组件时其他相关决定先转复核，不自行恢复其中一笔。 |
| `create_refund_group` + `decide_group` / `reopen_group` | 先人工提出候选，再明确确认/拒绝/拆分；至少两来源、最多一个钱包、同额同币种且分类域合法，无钱包另需明确确认。确认/拆分使旧相关资金决定失效，不自动迁移代表。 |
| `refund_links` / `refund_sources` | 同一只读快照派生当前状态、待修复原因；不修库、不写审计。 |
| `transactions` | 保留gross源行/金额/日期/类型与原过滤规则；只更新派生的退款待处理元数据。 |
| `spending_view(basis=None)` | 唯一净额入口；默认读取当前空间cash设置，也可显式指定original_purchase_month。只在内存产生负支出调整，不把退款当收入、不落入transactions。 |

投影行区分`source`与`refund_adjustment`；调整项带`record_count=0`，不增加消费/交易笔数。保留`gross_amount_cents`、`confirmed_refund_cents`、消费/退款实际日期、原始来源ID、决定ID、口径、计算时间及算法。证据分为Transaction、RefundAdjustment、RefundDecision；决定含消费/退款全部成员、组和确认快照。

金额汇总、预算、分类占比、记录估算及问答计算器已能处理这个带签名的frame，但**桌面/Web入口尚未改为调用它**。当前阶段的跨计算器检查不替代M2-4的全页面投影契约检查。

## 已观察的结果

**373项完整回归通过，34.11秒**；保留M2-1及以前全部322项原测试，新增51项，无失败/错误/跳过。六组现有源码桌面自检（general、M1a、round5/6/7/8）通过；M1a仍120→60→120元。

另覆盖：

- 累计恰好100元可确认，超1分拒绝；两条消费资金腿共享一个上限；原消费100退100后改80，相关决定复核，不形成−20的单笔消费。
- 同退款跨源关联两个消费、库内既有80+30超额确认，全部相关抵扣排除；无关有效退款仍抵扣。查询前后库字节/审计不变，新确认拒绝且不写。
- 两条退款先分别确认，再确认同退款组：旧决定全部复核；重新确认代表只扣一次。拆分、重新核对或重新确认组，都不会自动重新确认金额。
- 两个独立连接同时确认同一退款、同事件不同消费、两笔80争用100额度：仅一个成功；两笔30在100额度内则两个都成功。没有丢失更新或超退。
- 审计故障注入：确认、撤销、组确认/拆分及其失效更新整体回滚，无半决定。
- 早于消费、非人民币、普通收入/转账冒充退款、错分类、来源删除、无独立退款流均不产生抵扣。
- 常规编辑/缩小金额、消费或退款组变化、删除钱包/银行批次经过基础失效钩子并保留证据。两端删除后净额恢复当前gross。
- 只有退款月份允许负净额；预算100、净使用−30时剩余130；零/负占比分母显示不适用；负历史均值原样保留并返回`requires_explicit_budget=True`，负未来预算仍被规划函数拒绝。
