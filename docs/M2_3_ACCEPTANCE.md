## 已确定的契约

**重新确认采用B**：有效confirmed关联必须先撤销，再重新确认。直接重复提交、更换原消费或仅改说明均拒绝且不写。原有更新分支用于candidate/rejected/needs_review，不能描述为“原地修改有效确认”。撤销/重新确认保留完整旧新审计；旧关联ID可继续复用，历史不会被覆盖掉。

**继续全局阻止新确认**：任何无效confirmed都会阻止新确认。`refund_confirmation_blockers()`和`RefundReviewRequired.blockers`给出关联ID、原消费/退款ID、原因、相关关联ID及inspect/repair/revoke动作。M2-4必须据此列出具体阻塞并提供查看来源、定点修复或撤销入口，不能只显示“不能确认”。当前交付的是后端出口，不声称按钮已接入。

`repair_refund_links(identifier=...)`按相关组件修复：所选决定和与其相连的退款决定一起转needs_review，无关组件保持原样。无identifier是明确的全量修复。修复保留确认时context和原始账单，只持久化待复核状态、原因审计，不自动更换代表、不重新确认金额。重复修复返回0，不再写库或添加审计。

组件依据当前有效事件成员及已保存确认快照识别，不把所有历史未确认组永久当成一个消费。组成员即使被外部删空，已保存的组ID/成员仍用于找出旧退款决定；损坏context则显示待复核，不能猜测重建证据。

## 实现

| 部位 | 改动 |
|---|---|
| 退款维护 | 新增定点/全量修复、结构化阻塞列表、统一`maintain_links`；组与退款维护共用一个BEGIN IMMEDIATE事务。 |
| 事务边界 | 单条分类、模型建议接受、撤销批量、导入/重新导入、演示替换、扫描和候选清理补齐读前写锁；金额/分类/组状态/失效审计一起提交或回滚。 |
| 启动/恢复 | 可写启动及恢复后统一重验组与退款；只读启动不维护。恢复失败以恢复前快照回滚业务数据/审计。既有迁移和历史语义修复仍有各自原有流程。 |
| 组维护 | 消费组和退款组都能只读显示失效原因；显式修复使旧相关退款失效。消费组异常成员角色也恢复独立计数，避免读时和修复后统计不一致。 |
| 来源再导入 | 软删除来源明确重导入时保留ID，旧关联仍需重新确认，不能因原ID复活而自动抵扣。 |
| 原因/证据 | `refund_sources`补齐被牵连的待复核原因；持久化后从审计恢复原因，缺审计时给通用说明。`refund_link_evidence`提供保存的context、当前来源/原始行/hash、编辑前值、关联/组/批次审计及有效状态。 |
| 退款候选 | 同成员集合再次提交复用候选，不覆盖第一次说明或增加审计；旧重复候选维护时归档为stale并记录保留组，不删除证据。消费扫描只刷新消费候选，不再使退款候选过期。 |

“已关联/待处理”仍由有效关系派生，源退款状态保持refund_pending。`transactions()`仍为gross；普通有效数据的金额和过滤规则未改。净额读取、退款来源、待处理汇总和关联状态在同一套重验规则下保持一致。

| 维护路径 | 本包实际测试 |
|---|---|
| 单条编辑 | 金额/日期/商户/说明/分类/类型分别作用于原消费和退款，保存原确认context和编辑前值，当前来源可核对。 |
| 分类全部入口 | 单条、批量、模型建议接受、撤销批量，分别覆盖消费代表、资金腿、退款；模型只测接受服务，不调用真实模型。受保护标签/无变化操作不使有效资金决定失效。 |
| 失败回滚 | 多条分类中后续出现类型冲突，前面的分类和失效一起回滚；编辑/分类/撤销/删除/演示替换的审计故障均无半更新。 |
| 两端批次删除 | 真实通用导入将消费和退款放在独立批次，分别删除消费端、退款端；净额恢复当前gross，原始行/hash/删除审计保留。 |
| 消费组/退款组 | 两类组分别确认、拆分、重新核对；旧资金决定都需重确认。另测空成员和异常角色的只读发现与定点修复。 |
| 演示替换/清理 | 替换原消费月，旧退款决定失效；清理使用现有批次软删除路径，清完不重播100笔。没有新增清空功能。 |
| 来源重导入 | 交易软删后重导入、批次删除后实际重新解析导入，保留来源ID/hash，旧确认不会自动恢复。 |
| 启动维护 | 日期变化、消费组变化、退款组变化、分类域冲突均持久化待复核；不自动修正非转账旧错分类；再次启动字节不变。 |
| 备份恢复 | 有效快照恢复原有效决定；无效快照恢复后转复核，输入快照不变；维护故障后恢复前业务数据/审计完全还原。 |
| 只读/定点修复 | 每个动作后交叉核对spending_view、refund_sources、refund_links、pending_refunds、gross元数据、证据和审计；查询前后库字节/审计均不变。所选组件修复不影响无关组件。 |
| 幂等/并发 | 重复修复返回0且字节/审计不变；两个独立连接同时修复只执行一次；同成员候选并发提交只产生一个候选及一条提出审计。 |
| 维护原子性 | 组维护已写入后，后续退款修复审计失败，组/退款一起回滚；多决定修复在第二条审计失败时全部回滚。 |
| 异常元数据 | 损坏JSON、空/错误context结构、无审计的旧needs_review均可只读解释和修复，不自动生成缺失事实。 |

上述“字节不变”是查询及幂等调用前后检查，不是要求有意写操作不改变数据库文件。恢复失败比较完整业务行/对象/审计；SQLite备份还原可改变文件头，不宣称恢复操作本身逐字节还原原文件。并发用例覆盖确认（M2-2）、修复和候选提交，不构成多实例并发恢复认证。

定点实验：两组独立消费，第一组有两条相关退款、第二组一条退款；外部改日期后3条confirmed只读均待复核。选第一条修复返回2，仅剩第二组件阻塞；重复返回0且SHA256不变；修复另一组件返回1后阻塞清空，但净额仍为gross 200元。人工重新确认第一笔30元后才成为170元。每阶段查询字节均未变。
