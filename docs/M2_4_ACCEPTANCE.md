# M2-4：全页面净额、退款处理与口径契约验收

日期：2026-11-04。基线：用户通过的 M2-3 `18336e5`；开发分支 `m2/refund-net`。本包实现桌面/Web 接入，供独立评审。模式仍为 5，未修改迁移实现、个人账本、安装版或发布版本；稳定版仍为 v0.8.5 / 模式 4。实际打包 EXE 和发布属于 M2-5。

## 四个关口

| 关口 | 实现与验证 |
|---|---|
| 可操作阻塞 UI | 桌面“退款与统计口径”的“待复核与阻塞”页合并失效退款关联、无效/待复核退款组。显示关联/组 ID、原因和相关 ID，可查看来源证据、定点修复、撤销关联/拆分已确认组。Web“退款与口径”提供同一服务出口，关联历史有明确撤销入口。 |
| 净额唯一入口 | 桌面概览、账本摘要、预算、洞察、规划、问答、消费对账摘要以及 Web 全部统计接 `spending_view`；`spending_totals` 拒绝非净额投影。源记录、编辑、分类、退款选择和证据保留正金额来源。AST 契约门禁与同夹具实际界面操作均通过。 |

| 派生退款状态 | `refund_sources`、待处理摘要、源账本计数说明、概览与问答统一区分“已关联/待处理/待复核”。源行仍是 `refund_pending`；有效关联不显示待处理，失效关联不再扣净额。损坏 context 牵连的组成员也给出待复核通用原因。 |

## 用户可完成的处理路径

桌面概览、账本、预算及设置均可进入“退款与统计口径”；Web 导航增加“退款与口径”。先在“退款来源去重”核对两个来源、提出候选并明确确认，再在“退款流水与关联”选择原消费、核对完整退款金额后确认。首版只提供两来源操作，不扩展批量/三成员 UI。

**继续采用 B**：有效已确认关联的确认按钮禁用；要改原消费或说明，先在关联历史撤销，再重新确认。服务层也拒绝直接重确认。选择退款时会同步选择其关联历史，避免撤销另一条关系。

全局无效 confirmed 仍阻止所有新确认。被阻止后可以进入具体事项：查看当前来源与原确认快照、定点修复相关组件，或撤销。组异常也列出，避免漏掉一半；修复仅保存待复核，不修改来源、不自动恢复抵扣。需要修改金额/分类时，桌面可“定位原消费/定位选中原始记录”，使用现有源记录编辑；组修好后明确重新核对、确认，再重新确认退款。已保存的 needs_review 组不能反复“修复”假装重新有效。

窗口绑定打开时的空间；切换主窗口空间后，旧窗口写操作被拒绝。只读打开/刷新/查看证据不做隐式修复。Web 会话按空间保留 Store，普通 rerun 不再重新触发可写启动维护；首次可写打开仍遵循既有启动维护契约。

一笔退款只能以**完整金额关联一个原消费**，不拆覆盖多单的退款。原消费只有“已退款”文字而缺独立退款流水时，提示“无法确认净额”，不克隆流水。角色不明的旧消费必须人工确认原消费角色并留审计；确认角色不等于确认退款。

## 同一夹具的金额核对

夹具实际经过微信 CSV、银行模板 XLSX 导入：两来源消费 100 元（9 月），两来源退款 30 元（10 月）；人工分别去重后只抵扣一次，10 月餐饮预算 100 元。金额均以整数分处理。

| 指标 | cash | original_purchase_month |
|---|---:|---:|
| 9 月净支出 | 100 元 | 70 元 |
| 10 月净支出 | −30 元 | 0 元 |
| 10 月预算净使用 | −30 元 | 0 元 |
| 10 月预算剩余 | 130 元 | 100 元 |
| 全部月份消费总额 / 确认抵扣 / 净支出 | 100 / 30 / 70 元 | 100 / 30 / 70 元 |

概览、源账本旁净额摘要、预算、问答、规划历史输入及 Web 实际控件使用同一夹具核对。源记录表保留原始日期/金额，可编辑；**净额摘要按选定月份统计，不随源记录文本搜索改变**，界面明确标注。净额导出单独提供，含负抵扣项、实际退款日期、决定/来源标识和 basis，不能把调整项当作源账单编辑。

规划沿用“所选历史范围内，存在本口径计入明细的月份”计算均值：上述现金口径含 9/10 月，均值 35 元；原消费月口径仅 9 月有计入明细，均值 70 元。提示没有计入明细的来源月份及退款回溯可能性，不宣称已导入账单完整。历史均值为负时保留真实负数、清空自动填入的未来预算，要求明确非负预算后才能比较方案；不把退款回流预测成持续收益。

趋势支持负数/零轴；分类分母为零或负数显示“占比不适用”，不制造百分比。预算进度条限制视觉范围，真实负使用额及可超过额度的剩余数值完整保留。

## 问答与证据

明确问“消费总额”从净额投影中的来源项计算 gross；“净支出/支出”使用当前 net，未重新调用 gross getter。已导入来源但在本口径没有计入明细的月份，可以回答 0，并附来源覆盖/排除原因证据；没有对应来源的月份继续回答数据不足，不能把未知当 0。

增加有明确范围的本地查询，例如“2026-10 退款抵扣多少”“2026-10 已关联退款多少笔”“待处理退款金额”“退款待复核多少”。**抵扣**按当前口径归属月计算；**退款状态/完整退款金额**按真实退款发生月统计，文案明确二者可能不同。问答、trace 和导出标 basis/amount_basis，来源状态查询提供 RefundSourceStatus 等分型证据，不调用模型计算金额。不支持的预测仍拒答。

## 投影门禁的边界

[`finance/projection_contract.py`](../finance/projection_contract.py) 扫描根目录 Python 入口和 `finance/**/*.py`，新增产品文件自动纳入。17 个受保护金额入口须调用 `spending_view` 或有运行时检查的 `spending_totals`；9 个源读取用途按**文件 + 函数**逐项允许，不按整 UI 文件放行。

门禁拒绝产品 gross `transactions` 属性/方法别名、未授权 `source_transactions`、私有源工厂、已识别的反射取数及直接交易 SQL；检查来源局部别名、过滤/索引链和 `self.source_frame` 的统计聚合/金额计算入口。19 项静态回归含故意新增页面、假净额调用后继续用 gross、方法别名、反射、SQL、源函数内聚合和删除必要入口等反例。

这是可执行的回归约束，**不是对任意动态 Python 的形式化证明**。底层投影/数据库模块有显式信任边界，工程自检例外限于指定函数；同时用真实界面与业务夹具核对数值，不能只凭静态出现一次 `spending_view` 就宣布一致。
