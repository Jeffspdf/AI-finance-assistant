## 已确认的产品口径

用户本轮已选择：默认现金口径；预算按净支出；同时保留消费总额。原消费月口径可切换，切换只改变计算，不改原始日期/金额。退款不算收入，未关联退款保持待处理，单笔累计退款不得超过原消费。

现金口径中，只有上月退款而没有本月消费时，**本月净支出允许为负**；“不得负消费”约束的是单笔消费不得超退，不能把月净额截断为0。历史负净额也不能直接充当持续负预算或收入。

真实数据与试用人员当前尚未具备。用户选择先准备验证工具和采集模板；G-DATA保持未完成。设计确认后，M2-1仅对独立合成测试库执行模式5迁移与退款不变量校验，未迁移个人账本或更新已安装客户端。

## 数据模型与不变量

模式5增加两张表（M2-1已实现），保留交易金额为正整数分的约束：

```text
refund_links(
  id PK, refund_txn_id UNIQUE FK, original_txn_id FK,
  amount_cents CHECK >0,
  status [candidate,confirmed,rejected,needs_review],
  reason, confidence, algorithm_version,
  context_json, created_at, decided_at, decided_by
)
ledger_settings(key PK, value, updated_at)
```

`ledger_settings.spending_basis`按演示/个人库分别保存cash或original_purchase_month，默认cash；预算固定采用当前口径的net。API配置继续独立于账本。

M2-4切换时明确提示“将重算当前空间所有净额，不改原始账单”，保存切换时间和旧/新值审计。图表、导出和证据标明当前口径；M2-1只写初始默认值，不提供未经审计的设置接口。

`context_json`保存确认时的消费/退款代表、成员ID、金额/日期/分类与关键状态；audit_events保存每次决定的旧/新快照。context不是事实来源，读取时必须用当前来源和组关系重验。

复用link_groups.kind=refund_duplicate及link_members.role=refund，不与purchase_duplicate混用。仅**有效确认退款事件**的一个代表可进入退款关联。UNIQUE(refund_txn_id)只防同一原始行重复关联，还必须事务校验：

1. 同一个逻辑退款事件不能由钱包/银行两条来源分别抵扣。
2. 退款上限按**去重后的同一消费事件**累计，不能各对一条消费资金腿各享一次上限。
3. 选中资金腿时先解析到当前消费代表；存在歧义、事件发生变化或被其他决定占用时拒绝确认并要求复核。
4. 退款必须是明确独立退款来源、同币种、日期不早于原消费；首版一笔退款只关联一个原消费，金额为该退款事件的完整金额，多次部分退款通过多条退款实现，不做任意拆单分配。
5. 超额确认不抵扣，记录/显示needs_review；若消费变小导致累计超额，相关确认全部进入复核，不能自行挑一条保留来凑上限。
6. 合并/拆分消费或退款组后，所有受影响的退款决定先失效并保留证据，用户重新确认；不自动把资金决定搬到新代表。

M2-1的`validate_refund_link`仅提供一致只读快照内的校验，不能占用退款额度。M2-2的确认必须在同一个`BEGIN IMMEDIATE`写事务内重新校验并保存，不得直接使用先前预览结果写入。相关旧上下文失效时校验拒绝继续；持久化`needs_review`及审计属于M2-3。

## gross与net的共享投影

`transactions()`保持现有gross接口。新增`spending_view(basis=None)`作为唯一净额入口：普通收入/支出/转账来自当前有效gross投影，退款决定生成**只在内存中的负支出调整项**，不写入transactions。

- cash：调整项归退款发生日期；original_purchase_month：归原消费日期。
- 分类/商户追随原消费，独立保留退款真实日期、来源行及决定ID，不能把改过的投影日期伪装成原始日期。
- 每个调整项可展开原消费、消费排重组、退款、退款排重组、确认金额、统计口径、计算时间与算法版本。
- 消费总额、已确认抵扣、净支出分别展示；净额=总额−有效抵扣，退款不出现在收入合计。
- 统计读取重验失效决定并安全忽略抵扣，返回repair_pending和原因，不写库；显式维护负责持久化needs_review和审计。
- 查询笔数使用真实交易/消费事件数，不因一条抵扣调整增加一笔“消费”。
- 分类占比在净支出分母≤0时显示不适用，不能除零或生成误导百分比；趋势图支持负值与零轴。
- 预算额度保持非负，净使用额可以为负、剩余额度可大于原额度，明确是退款回流影响。
- 规划展示真实历史净额；若平均净支出为负，要求用户明确设置非负未来预算，不能静默用负预算预测持续收益。

账本继续保留原始正金额来源和计数说明，摘要另读同一净额投影。用户筛选月份时，消费总额和退款调整均按所选basis过滤，不能先按原始退款日期过滤后再回溯。

M2-4单独增加投影契约检查：概览、预算、洞察、规划、问答及Web的金额入口必须接入`spending_view`；源账本、退款来源、编辑和证据窗口仅在明确列入允许范围时可以读取gross。检查应定位到调用函数/用途，而不是整文件放行；新增统计入口绕过共享投影时测试失败。另用同一有退款夹具核对各入口数字，防止仅增加调用但仍用gross求和。

## 生命周期与写入边界

| 动作 | 维护 |
|---|---|
| 导入独立退款 | 仅pending，不创建确认抵扣；留来源/批次。 |
| 原消费行只有“已退款”状态 | 保留角色待复核；不克隆退款。需要用户明确该行是原消费、并有独立退款来源后再关联。缺流水时不能仅凭状态扣净额。 |
| 确认退款重复组 | 校验同一退款证据；事件归并后旧相关退款决定失效，重新确认一次。 |
| 确认退款关联 | 在一个事务内检查源状态、逻辑事件唯一、累计上限、上下文，更新决定和审计。 |
| 拒绝/撤销关联 | 撤销抵扣，保留决定历史，不删除来源。 |
| 编辑消费/退款金额、日期、类型、分类 | 先失效相关决定；重验上限/事件；一次事务完成，查询立即不抵扣失效项。 |
| 确认/拆分/重新核对消费或退款组 | 成员/代表变化使相关退款决定待复核，避免按旧代表继续扣。 |
| 删除任一关联批次 | 软删来源，同事务使相关组/退款决定失效；另一端退款回待处理。 |
| 恢复备份 | 预览、当前快照、暂存迁移、恢复完整性检查、显式重验；任一步失败恢复前快照。 |
| 只读查询/窗口 | 不迁移、不修复；使用当前有效投影并提示待修复。 |

所有维护路径包含普通编辑、单条/批量分类、模型分类、撤销批量、演示月份替换/清理、批次删除、组决定和恢复；不能只接编辑按钮一个入口。

额外必须覆盖：退款恰好等于上限、超1分、同消费已排重的两个来源分别被选中、先确认两条退款后再去重、撤销退款组、退款日期早于消费、币种/类型不符、原消费只有退款状态、缺失原消费、零/负分母、只有退款的月份、模拟故障事务回滚、只读数据库字节/审计不变。

这些是验收包，不以文档中的5–8天作为工期承诺。不加入新依赖，不调用模型处理退款，不扩展OCR/移动端/自动同步。

## 真实验证并行安排

当前已准备[离线验证协议与工具](REAL_VALIDATION_PROTOCOL.md)，默认采集目录为本机`.validation-private`，已在.gitignore之外再受源码归档白名单排除。只有空模板，没有真实导出、人工标注者或用户试验结果。

工具分别计算候选质量、独立召回、分类覆盖/准确率、问答数值/口径依据、任务障碍与耗时；synthetic始终标练习，缺盲扫分母就不输出recall，完整表格也只进入人工验收，不自动宣布“真实验证通过”。

M2可用后团队再组织8–12份授权脱敏文件、双人标注200笔、独立全量扫描和5位定性试用。M2的工程关口G-M2和真实关口G-DATA分别记录；数据暂缺不伪造，也不因此把客户端退款功能说成完成。
