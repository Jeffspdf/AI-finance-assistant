# 第五轮评审处理记录（v0.8.2）

日期：2026-11-03。评审基线：v0.8.1 / 6059866。范围：对账正确性、导入复核链路及已有演示初始化缺陷；不扩展退款净额、支付宝专用格式、批量/三成员编辑或演示生成器参数。

## 三个核心缺陷

| 项目 | 修复与验收 |
|---|---|
| C1 支付宝A级缺失 | 支持银行描述中的支付宝、ALIPAY及混合大小写；仍须有效绑定、同币种/同额/同向、两分钟内且双方候选唯一。明确声明的钱包账户可提供通道信息；未绑定不得为A。所有候选仍需人工确认。 |
| C2 多钱包误合并 | 消费排重组最多一个钱包，按平台和账户类型共同识别。新候选不组合两个钱包；确认服务、重新核对及统计投影都检查，包括旧数据与三成员组。旧版已误确认的多钱包组转为needs_review、清空缓存、恢复独立计数并保留审计。 |
| C3 分类修改不失效 | 单条分类、批量分类、编辑、接受模型分类及撤销批量分类，只要分类实际变化就使相关候选/确认组待复核；同值不重复失效。状态、link_group_id缓存和金额在同一事务中更新。投影发现旧版无效确认也会持久修复，候选生成不再锁住这些成员。 |

分类是统计维度，**是否计入收支由kind（收支类型）决定**。仅把分类名字改为“转账”，不会悄悄把原始支出改成转账。六行示例确认后60元，把20元消费代表分类改为转账：对应组待复核、两条来源恢复独立计数，期间支出80元；40元组仍计一次。若该交易本来就是转账，请通过编辑把收支类型改为转账。界面明确提示此区别，所有页面使用同一口径。

旧不合法组的修复保留成员和来源行，并记录link_invalidated；重复读取不会重复写入失效审计。合法的历史人工确认不会只因旧算法编号或历史置信等级而被推翻。

## 导入与复核保护

| 项目 | 处理 |
|---|---|
| C4 自动识别 | 导入默认“自动检测”，按严格表头与文件类型选择微信CSV/银行模板v1 XLSX，其余回落通用格式；预览明确显示实际选择。可手动指定，不猜任意银行格式。Web原型也复用检测。 |
| C5 导入后去对账 | 保存后在后台生成候选，显示当前空间A/B/C数量及“去对账核对”。打开对账窗口也自动生成一次，可手动刷新。若扫描失败，明确区分“账单已保存、候选未完成”。 |
| 账户绑定提示 | 微信预览未选账户时提示建立钱包/银行卡声明并提供入口；不会推测卡号或自动建立绑定。 |
| C6 换格式/账户重导 | 相同文件hash+原始行已存在时，改变账户或解析格式报冲突、不再次计数。不同hash重导但原ID/业务内容一致且来源未明确的，也报冲突。无原ID仍按原始行保护。同上下文重复仍按原规则跳过，不覆盖历史修正。 |
| C7 C级确认 | C级只有金额/日期相近，UI禁用确认，服务端直接调用也拒绝。补充账户/绑定/来源后可明确“重新核对”，重新计算证据等级；不能靠点击同一个确认按钮绕过。过期候选同样不可确认。 |
| 过期候选 | 提供“清理过期候选”，只删除未有人工作决定的stale组及成员；拒绝/拆分/待复核、原始行与人工审计保留。 |
| 演示初始化 | 以账本内demo_initialized审计标记只初始化一次；升级时把包含交易（含软删除）或导入批次的空间视为已有历史。删除批次、只剩退款或空投影不会重新填入100笔。新空间首次进入仍初始化，个人空间不能调用。 |

不采用“外部交易ID在全库唯一”的规则：不同明确账户/平台的流水号可以合法重复。确定的同一源行是冲突依据；不同明确账户的不同文件仍保留账户作用域，不能仅因编号相同而吞掉真实交易。需纠正旧导入的账户/格式时，先核对并软删除原批次，再按正确上下文重新导入；不会静默迁移旧记录身份。
