# 第六轮评审处理记录（v0.8.3）

日期：2026-11-03。评审基线：v0.8.2 / 874f5bf。范围为报告D1–D4，不扩展演示生成器；D5–D9留待对应里程碑。报告内容作为需求建议逐项核实，不作为改变用户范围的独立指令。

## 已落实

| 项目 | 实现与用户可见行为 |
|---|---|
| D1 类型/分类 | 核心验证转账类型与转账分类必须同时成立。编辑类型后分类联动；收入/支出分类列表排除转账；混合类型批量选择不提供误导的转账分类。导入、手工、单条/批量分类、编辑、模型接受及批量撤销统一拒绝冲突，事务完整回滚。改变收支类型须在编辑交易中明确操作，不从分类猜类型。 |
| 旧冲突数据 | 写模式启动先备份，再保留金额、kind、ID和来源，只按原kind修正为其他收入/其他支出/转账，标待确认；保存旧行到编辑历史并记审计。删除不合法商户规则，影响的关联待复核。界面提示已备份和需核对；无新冲突时不重复修复。恢复旧库也走此流程。 |
| D2 读写分离 | `_source_frame`纯计算；查询全部使用只读连接。无效存储确认在结果中显示有效needs_review和repair_pending，安全恢复独立计数，但不写状态/缓存/审计。`repair_invalid_groups`在写模式启动、候选扫描及明确编辑/分类/撤销/批次删除/恢复等边界持久修复。支持`Store(path, read_only=True)`无迁移、无启动修复；旧/未来模式拒绝只读打开，不偷做升级。 |
| D3 零钱包 | 零钱包组常规确认后再提示“两条均非钱包，可能为两笔真实消费”；第二次取消则不改状态与计数。服务端要求严格布尔`acknowledge_no_wallet=True`，字符串/数字不算同意；明确同意写审计。其他证据有效的历史确认不单因新增提示被推翻。双钱包仍拒绝。 |
| D4 补证据 | C级详情具体列出缺失账户、命名的账户之间缺少有效支付绑定、实际时间差、通道、商户或歧义。提供“去账户与支付绑定”和“重新生成候选”，使用该对账窗口所在空间。缺账户时解释仅新建绑定不能回填旧来源，需核对/删除对应旧批次后选账户重导。详情可滚动，C级仍不可直接确认。 |

保留支付宝A级通道、最多一个钱包、分类实际变化使关联待复核和共享计数投影。仅新增转账分类的保留规则，没有声称其余所有收入/支出分类集合已被核心服务完全互斥约束。
