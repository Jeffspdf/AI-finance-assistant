日期：2026-11-04。评审基线：v0.8.5 / a4055b4；功能代码提交686a6c7。结论：同意M1a最小闭环通过验收，当前未核实出需要再发运行时补丁的阻塞缺陷。本轮新增复核证据和工程记录，客户端/模式保持0.8.5/4，公开安装包和源码资产保持原内容。

## 对报告的独立判断

| 报告内容 | 复核结果 |
|---|---|
| F1–F4通过、M1a可收口 | 与当前代码及第八轮测试/实际EXE证据一致。接受的是限定来源、人工确认、本地单用户应用的最小闭环，不将其扩大为任意银行格式或真实准确率认证。 |
| 历史分类逐条修正 | 待修正窗口的直接操作确实为逐条定位/编辑。主账本已有多选批量分类、同商户同类型应用和撤销；但这些不等于完整的历史异常批量复核流程。G1可选，不作为验收失败或本轮新增范围。 |
| “无效商户规则不可见” | 这一判断不准确。设置→分类记忆→管理分类记忆调用merchant_rules()列出全部规则，没有隐藏旧收入/支出错分类规则；已有删除选中规则的入口。交易分类待修正列表不显示规则，是交易和规则的职责区别。缺少的只是专门的失效标记/筛选，可选增强无需重新造一个列表。 |
| 旧规则未自动清理 | 属于既定保留策略。导入会验证并忽略不合规的收入/支出规则；用户仍能查看/删除。旧转账语义冲突规则另有备份后维护路径，不能一概表述为所有无效规则都只忽略。 |
| 备份“显示身份/二次确认/硬链接校验” | 界面显示文件名、大小、用途和预览；设备/文件标识用于内部校验，没有直接展示给用户。删除是一次人工确认加确认身份/删除前程序复核，不是两个删除确认框。硬链接按目录项语义处理，不是全面阻断硬链接。 |
| 接受TOCTOU残余、不继续增加复杂度 | 与现有本地单用户边界相符，保留第八轮限定表述；不把“可接受”写成“彻底消除”。 |
| 进入M2 | 是后续阶段建议，G3–G7属于新的业务里程碑。本轮收口当前范围，进度记录不把这些建议写成已开始或已交付。 |

“全部来源”具体指当前空间未删除来源，含排重资金腿与跨月记录；软删除记录仍保留追溯/审计，但不出现在当前待修正列表。报告中“删除前来源”不能解释为已经删除的来源也列入。

## 本轮复核证据

`python scripts/verify_round9_review.py`使用临时演示库注入一条合成旧规则（收入/餐饮）及一条有效规则，在既有设置入口中验证：

- 旧无效规则确实显示；只查看时数据库字节不变。
- 选择旧规则并点击原有删除按钮后，仅该规则删除，有效规则保留。
- 交易来源记录前后完全相同，无Tk回调错误。

[结构化结果](round9_review_validation.json) · [既有规则管理入口截图](screenshots/round9/existing_invalid_rule_visible.png)。截图只含合成商户，不是个人账本。

本轮另执行既有测试`tests/test_round2.py::test_manual_learning_copy_and_undo`和`tests/test_round7.py::test_category_sets_and_legacy_income_expense_are_not_rewritten`：**2 passed in 1.10s**。前者验证规则应用/删除、批量与撤销，后者验证旧错分类保留、无效收入规则不应用到新导入和明确修正。

运行时功能没有改动，因此没有重新打包或重复全量UI/联网下载验收。完整**247项**、实际EXE六阶段、原生150%DPI和37,737,239字节安装包下载SHA256等仍引用[第八轮记录](ROUND8_RESPONSE.md)及其原始执行证据，不把本轮两个选定测试说成重新跑过完整247项。验证工具脚本不计入新增pytest数量，原测试集仍为247项。
