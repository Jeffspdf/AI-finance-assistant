# 更新检测与下载通路复核（v0.7.4）

日期：2026-11-03。用户已手动升级0.7.3，但报告检查更新仍失败，0.7.2没有发现新版本。

## 可确认的证据

**本轮随后找到的直接根因：本地构建的EXE缺少运行时SSL模块要求的相邻公共证书资源 `codex-rejected-cas.pem`（906字节）。真实EXE联网诊断在 `ssl.SSLContext.__new__ → load_verify_locations` 抛FileNotFoundError，任何HTTPS请求尚未发出就失败。下面的源代码执行成功不能代表原EXE成功。此前0.7.3的连接超时/通路修复没有解决这一打包缺件，原“检查更新未完成”通用提示也遮蔽了它。**

构建脚本现通过 `packaging/runtime_tls_assets.py` 检测构建解释器所需的该公共资源并随包带入SSL模块目录。官方CPython没有此额外资源时不添加。没有修改SSL实现、没有移除运行时信任约束、没有关闭证书或主机名校验；也不修改Windows证书库。打包自检新增实际SSLContext初始化，避免只跑离线账单自检而漏掉HTTPS无法初始化。

读取安装二进制确认当前0.7.3。执行0.7.2原版检测代码，当次系统代理请求GitHub API返回403/remaining0，官方latest页可识别0.7.3并判newer=true；带防缓存参数的请求也成功。因此不能说旧版一定无法识别，也不能用这次成功否定用户遇到的失败。

执行安装版0.7.3的更新模块：系统代理API同样403，官方页面当次成功；直连API当次200并正确返回0.7.3。故确认不同通路表现不同，尚未获取用户GUI失败瞬间的完整底层异常。桌面查看工具初始化失败，没有用UI截图冒充成功证据。

先前只验证函数与命令行网络下载不足以证明桌面EXE可靠。urllib全局opener复用及代理设置变化属于附加容错改进，不再将其写成已捕获的主要根因；本轮每次新建opener读取当前设置，同时添加实际打包EXE联网诊断。

## 修复范围

- 系统网络/直连分别请求官方API；解析失败也尝试下一通路。两条API均不可用，再对官方latest页面做两条通路检测。每次请求带时间参数与no-cache；跳转仍限制本仓库正式版本。
- 不修改系统代理、不附带用户GitHub或模型凭据、不使用第三方镜像。诊断只记录时间、客户端/远端版本、通路、HTTP状态/错误类型和验证结果，不记录代理地址、请求头、密钥或账单。
- 下载可从失败通路切换到直连并重新开始，校验及取消规则保留；磁盘权限、超额文件和校验错误不当成成功。对正在阻塞的单次网络读取，取消仍要等该次调用返回或超时，不宣称瞬时取消。
- 明确区分新版本/同版本/公开版本较旧/无法确认四种状态，只有不低于当前的官方安装包可点下载。
- 后台向界面报告清单/连接/切换通路阶段，写本机有界诊断文件。实际EXE提供 --diagnose-updates 和可选 --download-latest，执行同一实现且跳过主窗口/模型配置加载；不自动安装。

## 验证方式

离线测试模拟：系统代理403→直连API成功、代理返回HTML→直连JSON成功、所有API失败→受信官方页面、所有通路失败不判最新、同版本提示、禁止降级、传输中断后直连重下、取消不换通路、校验错误拒绝。

`scripts/verify_packaged_update_network.py`清除工具环境的代理变量，保留Windows系统网络设置，启动实际打包EXE，生成 `docs/packaged_update_network.json`。结果包含公开发布版本和本机各阶段事件，下载保存在临时目录并清除；这是软件网络路径验证，不是手动安装认证。

旧版二进制无法远程获得本轮修复，需要先安装修复版。公开GitHub发布与实际下载结果单独核对，不能把本地测试通过当成发布成功。

尝试直接为现有安装补入缺失资源时，当前自动执行环境被拒绝写入安装目录；没有改权限、覆盖现有不同资源、修改账单或Key。需由用户手动覆盖安装已补齐资源的新包。此前用户已手动安装0.7.3，因此不把这次自动写入失败归因于用户账号异常。
