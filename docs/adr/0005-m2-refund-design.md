# ADR 0005：M2退款净额设计

日期：2026-11-04。状态：M2-1/2用户已通过，M2-3维护服务及矩阵已实现，后续包待实施/验收。公开稳定版仍为v0.8.5、模式4，开发库模式5。[方案](../M2_GAP_AND_IMPLEMENTATION_PLAN.md)、[M2-1](../M2_1_ACCEPTANCE.md)、[M2-2](../M2_2_ACCEPTANCE.md)、[M2-3](../M2_3_ACCEPTANCE.md)。

1. 用户确认默认cash、预算采用net，同时展示gross。原消费月可切换。月净额可负，单笔累计退款不得超过消费；退款不作收入。
2. M2-1增加refund_links和ledger_settings，有限迁移4→5先一致备份，保留模式4历史checksum；只添加新表、索引及版本5记录，不重跑旧DDL。迁移失败回滚，未来版本拒写，恢复同样重验。历史checksum是迁移记录，不用于防篡改或签名验证。
3. refund_duplicate独立于purchase_duplicate，先人工确认跨源退款事件，再由一个代表关联原消费。物理UNIQUE(refund_txn_id)不足以防事件重复，服务层必须按逻辑退款/消费事件验证唯一与上限。
4. transactions()维持gross，新spending_view产生内存负支出调整。源金额与日期不改，全部金额入口复用，证据同时含原消费/退款/组/决定/口径/时间。统计计数不把调整项当新增消费，非正分母不计算支出占比。
5. 源编辑、分类各入口、组变化、批次删除、演示替换和恢复使相关决定失效并保留审计；组代表变更不自动搬运旧资金决定。读取纯重验，维护显式持久化。
6. 原消费显示“已退款”不等于存在独立退款流水。角色不明保持复核，不凭文字克隆退款或自动抵扣。用户确认原消费角色需要独立审计。
7. 真实数据当前未具备，仅准备离线工具与模板。工具声明、合成样本和表格填满均不等于真实验证；人工独立扫描分母、授权来源和最终验收仍由团队负责。
8. 一笔退款只能以完整金额关联一个原消费，不拆分覆盖多单的退款。原消费仅有“已退款”状态而无独立退款流水时不抵扣，UI须说明“缺退款流水，无法确认净额”。
9. 全局口径切换须提示将重算当前空间净额但不修改原账单，记录时间和旧/新值；图表和导出标注口径。预算剩余可大于额度，分类分母非正显示不适用；负历史均值要求明确设置非负未来预算。
10. M2-4单独验收全页面接入及投影契约检查，禁止新的统计入口绕过spending_view读取gross。M2-5才进行实际EXE验收和v0.9.0发布。
11. M2-2采用策略A：退款源行保持refund_pending，已关联/待处理由有效refund_links派生；逻辑退款组在待处理汇总中只计一个事件。旧类型/分类域冲突先修正再允许关联，不自动纠正。
12. 确认服务先BEGIN IMMEDIATE，再对全部confirmed进行当前事件/上下文/跨源唯一/累计上限重验，异常时拒绝且不写；预览不能作为确认依据。读取仅屏蔽失效组件，不影响无关有效组件；常规写入先使相关决定needs_review并留审计。
13. 重新确认采用B：有效confirmed必须先撤销，再重新确认，不能直接换原消费/改说明。全局阻塞策略保留，提供ID/原因/相关组件及修复/撤销接口；M2-4必须接入可操作出口。
14. M2-3显式修复只将失效决定持久化为needs_review，定点操作覆盖其相关组件而不波及无关组件；重复修复不写。保存旧context和原因审计，任何修复都不自动重确认。可写启动/恢复维护组与退款，纯只读调用仅重验。

M2-3已完成维护矩阵、定点修复、持久化原因/证据和候选幂等；UI及实际EXE仍未验收，未改写个人数据库或发布安装包。M1a功能冻结，超范围适配/性能/UI扩展须有实际触发数据再另行记录。
